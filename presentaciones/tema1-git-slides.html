01 · Introducción

¿Qué es Git?

Un sistema de control de versiones distribuido que registra los cambios sobre un conjunto de ficheros a lo largo del tiempo.

  • ▸Creado en 2005 por Linus Torvalds
  • ▸Objetivo original: gestionar el desarrollo del kernel de Linux
  • ▸Distribuido: cada máquina tiene el historial completo, no solo el servidor

HISTORIAL

01 · Introducción

La analogía de los puntos de guardado

Piensa en Git como el sistema de guardado de un videojuego. Cada commit es una fotografía completa del proyecto en un momento concreto. Si algo sale mal, cargas el último punto de guardado.

02 · Proveedores web

Proveedores de repositorios remotos

Git es una herramienta local. Para colaborar en equipo necesitamos un lugar centralizado donde:

  • ▸Compartir el código
  • ▸Revisar cambios antes de integrarlos → Pull / Merge Requests
  • ▸Gestionar incidencias y tareas → Issues
  • ▸Automatizar pruebas y despliegues → CI/CD

Los tres más usados: GitHub, GitLab y Bitbucket.

02 · Proveedores web

Autenticación: HTTPS vs. SSH

HTTPS
$ git clone https://github.com/usuario/repo.git # Pide usuario y token de acceso personal (PAT)
SSH
$ ssh-keygen -t ed25519 -C "tu@email.com" $ git clone git@github.com:usuario/repo.git # Ya no pide contraseña
GitHub y Bitbucket eliminaron las contraseñas normales vía HTTPS: se usa un Personal Access Token (PAT). SSH evita ese paso.

03 · Rama principal

Preparar cambios y .gitignore

bash
$ git status $ git add MiClase.java $ git add . # todo lo modificado $ git add -u # solo lo ya rastreado
.gitignore
# Carpetas del compilador / IDE /target/ /.idea/ *.class # Datos sensibles application-local.properties .env
cuidado  git add . añade absolutamente todo, incluidas contraseñas o configuraciones locales si no tienes .gitignore.
03 · Rama principal

Crear un commit

bash
$ git commit -m "Añade validación de email" # add + commit en un paso $ git commit -am "Corrige el cálculo del precio"
buenas prácticas
  • ▸Usa el imperativo presente: "Añade", "Corrige", "Elimina"
  • ▸Sé descriptivo pero conciso (<72 caracteres)
  • ▸Indica el por qué si el cambio no es obvio

04 · Ramas y merge

¿Por qué usar ramas?

Sin ramas, todo el equipo trabaja sobre el mismo código a la vez: código a medias mezclado con código estable, bugs difíciles de aislar, cero margen para experimentar.

Con ramas, cada funcionalidad vive en su espacio seguro hasta que está lista para integrarse.

04 · Ramas y merge

Crear y cambiar de rama

bash
$ git branch feature/login $ git checkout feature/login # forma moderna, en un paso $ git switch -c feature/login
convención de nombres
  • ▸feature/nombre nueva funcionalidad
  • ▸fix/nombre corrección de bug
  • ▸hotfix/nombre corrección urgente
  • ▸release/version preparación de versión
04 · Ramas y merge

El flujo de trabajo con ramas

  • 1Partir de main actualizado
  • 2Crear una rama para la funcionalidad
  • 3Desarrollar y hacer commits en esa rama
  • 4Fusionar la rama con main cuando esté lista
  • 5Eliminar la rama, ya integrada
bash
$ git switch main && git pull origin main $ git switch -c feature/registro $ git commit -m "Añade formulario" $ git switch main $ git merge feature/registro $ git branch -d feature/registro
04 · Ramas y merge

Merge fast-forward

Ocurre cuando main no ha recibido ningún commit nuevo desde que creaste la rama. Git simplemente mueve el puntero hacia adelante.

04 · Ramas y merge

Merge con commit de fusión

Ocurre cuando ambas ramas han avanzado por separado. Git crea un nuevo commit que une las dos líneas.

$ git merge --no-ff feature/registro -m "Merge: integra registro"
04 · Ramas y merge

Resolver conflictos

Ocurre cuando dos ramas modifican las mismas líneas. Git no puede decidir y te pide resolverlo a mano.

  • 1Edita el fichero, elimina los marcadores
  • 2Añade el fichero al staging area
  • 3Completa el merge con un commit
Saludo.java
<<<<<<< HEAD return "Bienvenido, " + nombre; ======= return "Hola, " + nombre + "!"; >>>>>>> feature/saludo

05 · Flujos de trabajo

¿Por qué necesitamos un flujo?

Un flujo de trabajo (Git workflow) establece las reglas que sigue el equipo: qué ramas existen, quién fusiona dónde y cómo se etiquetan las versiones.

  • ▸Qué ramas existen siempre y para qué sirven
  • ▸Quién puede fusionar en qué ramas
  • ▸Cómo se etiquetan las versiones publicadas
05 · Flujos de trabajo

Flujo 1 · Trunk-Based Development

Todo el equipo trabaja directamente sobre main. Apropiado para equipos muy pequeños o proyectos personales.

✓ simplicidad total ✗ errores llegan a producción
05 · Flujos de trabajo

Flujo 2 · Feature Branch Workflow

Cada funcionalidad se desarrolla en su propia rama y se fusiona a main vía Pull Request, con revisión de código del equipo. El flujo más común en proyectos medianos.

05 · Flujos de trabajo

Flujo 3 · Git Flow

RamaPropósito
mainProducción, recibe de release/hotfix
developIntegración continua de features
feature/*Parte de/fusiona en develop
release/x.yDe develop a main+develop
hotfix/*De main a main+develop

Diseñado por Vincent Driessen (2010). Ideal para software con ciclos de releases definidos (v1.0, v1.1, v2.0…).

✓ muy estructurado ✗ complejo, muchas ramas
05 · Flujos de trabajo

Flujo 4 y 5 · GitHub Flow / GitLab Flow

GITHUB FLOW

Solo main

Simplificación de Git Flow para despliegue continuo. Toda feature se hace en rama propia + Pull Request + revisión + merge a main desplegable.

GITLAB FLOW

Ramas de entorno

Extiende GitHub Flow con ramas pre-production y production para entornos de despliegue no automático.

05 · Flujos de trabajo

05 · Flujos de trabajo

Etiquetas (tags): marcar versiones

bash
$ git tag -a v1.2.0 -m "Version 1.2.0" $ git tag $ git push origin --tags

Las etiquetas marcan commits concretos como versiones oficiales del software.

06 · Errores comunes

Error 1 y 2

error 1

Commit en la rama equivocada

Trabajas en main por descuido en vez de en feature/....

✓ Crea siempre la rama antes de empezar a trabajar.

error 2

Olvidar git pull antes de empezar

Git rechaza el push: el remoto tiene commits que tú no tienes.

✓ Actualiza siempre con git pull antes de crear tu rama.

06 · Errores comunes

Error 3 y 4

error 3

Mensajes de commit sin sentido

"cambios", "arreglado", "wip"…

✓ Explica el qué y el por qué, en imperativo.

error 4

Versionar ficheros sensibles

Contraseñas, claves de API o configuraciones locales sin .gitignore.

✓ Define .gitignore antes del primer commit.

atención  Si subiste una credencial real, cámbiala inmediatamente: los bots escanean repositorios públicos.
06 · Errores comunes

Error 5, 6 y 7

error 5

Fusionar sin resolver conflictos

Dejar los marcadores <<<<<<< dentro del código.

error 6

Borrar una rama sin fusionar

Usa -d (protege) en vez de -D (fuerza) salvo que sepas lo que haces.

error 7

git add . sin revisar

Revisa siempre con git status / git diff antes de confirmar.
